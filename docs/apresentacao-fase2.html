Workflow de CI · .github/workflows/ci.yml

Dois jobs encadeados: só vira imagem o que passou nos testes

1

build-and-test

  • Checkout e instalação do .NET SDK 10
  • dotnet restore e dotnet build em Release
  • Versão 1.0.<run> gravada nas DLLs
  • dotnet test com relatório .trx
  • Resultado publicado como check no commit
  • Arquivos brutos guardados no artefato test-results

2

build-image

needs: build-and-test

  • Login no GitHub Container Registry
  • docker build pelo Dockerfile multi-stage
  • dotnet publish acontece dentro da imagem
  • Versão e SHA do commit entram como build args
  • Push com três tags para o GHCR
  • Em pull request constrói, mas não publica

Pós-Tech · Fase 2 · CI/CD

5

O artefato

Uma imagem por run, com a versão rastreável até o commit

A versão é 1.0.<número do run>. Ela vai para a DLL, para o label da imagem e para a tag. É assim que se confere, no destino, qual build está no ar.

$ docker inspect portfolio-api --format '{{.Config.Image}}'

ghcr.io/mlrneves/portfolio-api:1.0.42

TagPara que serve
1.0.<run>A que o CD usa. Uma por execução do CI
sha-<commit>Liga a imagem ao commit exato
latestSó na main. Conveniência para uso manual

Workflow de CD · .github/workflows/cd.yml

Dispara sozinho quando o CI fica verde na main

Gatilho

on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]

if: conclusion == 'success'

runs-on: [self-hosted, Windows]

1

Valida o secret PROD_JWT_SECRET antes de derrubar qualquer coisa

2

Baixa a imagem exata do run que o disparou, nunca a latest

3

docker compose up -d --no-build troca o container da API; o SQL Server e o volume ficam

4

Smoke test espera GET /health responder 200; se não responder, o deploy fica vermelho

5

Resumo do job com imagem, commit, run do CI e a URL do Swagger

A prova do deploy

GET /health: o deploy só é bom se a API e o banco responderem

GET http://localhost:5080/health

HTTP 200 OK

{
  "status": "Healthy",
  "totalDurationMs": 18,
  "checks": [
    {
      "name": "database",
      "status": "Healthy",
      "durationMs": 17
    }
  ]
}

🗃

Checa o banco, não só o processo

Se o SQL Server caiu, responde 503. A API sem banco não serve para nada.

🔑

Sem token, de propósito

O orquestrador e o smoke test não têm JWT. A resposta não expõe nada sensível.

🔍

Fora do Swagger

É um endpoint de infraestrutura. Na demo, abre direto no navegador e aparece no log do smoke test.

⏱

Smoke-Test.ps1 espera até 2 minutos

Tempo do SQL Server subir e das migrations rodarem. Sem 200, mostra os logs e falha o deploy.

Pós-Tech · Fase 2 · CI/CD

8

Segredos e ambiente

Nada sensível no repositório nem na imagem

Os segredos entram por Settings, Secrets and variables, Actions, e chegam ao container como variáveis de ambiente pelo docker compose.

SecretObrigatórioPara que serve
PROD_JWT_SECRETSimChave HMAC que assina os tokens. Mínimo de 32 caracteres. O deploy falha sem ela, de propósito
PROD_MSSQL_PASSWORDNãoSenha do sa do SQL Server em container. Sem ela, usa a de desenvolvimento do compose
GITHUB_TOKENAutomáticoLogin no GHCR para publicar a imagem no CI e baixá-la no CD
🔒

A chave de dev do appsettings.json só serve para rodar após o clone

⚠

Chave curta: a aplicação não sobe. Falhar no boot é melhor que token fraco
